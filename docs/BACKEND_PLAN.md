# Backend Plan — POS API (Hono.js)

> Dokumen ini menjadi acuan utama pembangunan backend POS.
> Digunakan sebagai referensi jangka panjang & onboarding anggota tim baru.

---

## 1. Overview

Backend untuk aplikasi Point of Sale (POS) berbasis mobile.
Frontend menggunakan **Flutter**, backend menggunakan **Hono.js + TypeScript**.
Database schema mengikuti [erd.md](erd.md).

### Struktur Repo
```
pos/
├── erd.md
├── BACKEND_PLAN.md
├── backend/           ← project ini
└── frontend/          ← Flutter project (dari team frontend)
```

### Keputusan Stack (Final)
- **Runtime:** Node.js 20+
- **Framework:** Hono.js + TypeScript
- **ORM:** Drizzle ORM
- **Database:** PostgreSQL
- **Package Manager:** pnpm

### Tujuan Backend
- Menyediakan REST API untuk fitur kasir, manajemen stok, dan laporan.
- Mendukung role-based access (admin, kasir, owner).
- Mudah diperluas untuk fitur masa depan (multi-outlet, diskon, member, dll).

## 2. Tech Stack

| Layer | Pilihan | Alasan |
|---|---|---|
| Runtime | **Node.js 20+** | Stabil, kompatibel luas (bisa swap ke Bun nanti) |
| Framework | **Hono.js** | Ringan, cepat, type-safe, modern |

| Linting | **ESLint** + **Prettier** | Konsistensi kode |
| Package Mgr | **pnpm** | Cepat, hemat disk |

## 4. Pola per Modul

Setiap modul mengikuti **4-file pattern** dengan tanggung jawab terpisah:

```
modules/<nama>/
├── <nama>.routes.ts      → Definisi route + binding handler + middleware
├── <nama>.handler.ts     → Parse request, panggil service, format response
├── <nama>.service.ts     → Business logic + akses DB (lewat Drizzle)
└── <nama>.schema.ts      → Validasi input/output via Zod
```

### Alur Request
```
HTTP Request
   ↓
Routes (apply middleware: auth, role, validation)
   ↓
Handler (parse input)
   ↓
Service (business logic + DB query)
   ↓
Handler (format response)
   ↓
HTTP Response (standard envelope)
```

### Standard Response Envelope
```typescript
// Success
{
  "success": true,
  "data": { ... },
  "meta": { ... }              // Optional (untuk pagination)
}

// Error
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "...",
    "details": { ... }         // Optional
  }
}
```

## 5. Implementation Phases

Pembangunan backend dibagi **8 fase**, dieksekusi berurutan.
Setiap fase bisa diuji & di-commit sebelum lanjut.

### Phase 1 — Project Initialization
- Inisialisasi `package.json`, install dependencies
- Setup TypeScript (`tsconfig.json`)
- Setup ESLint + Prettier
- Buat `.env.example`, `.gitignore`
- Struktur folder kosong (placeholder)

**Deliverable:** Project bisa di-build, lint, format.

### Phase 2 — Core Foundation
- `config/env.ts` — validasi env
- `config/database.ts` — Drizzle client
- `utils/logger.ts` — Pino setup
- `shared/errors/` — error classes
- `shared/response/` — response helpers
- `src/app.ts` + `src/index.ts` — minimal Hono app + healthcheck

**Deliverable:** Server bisa start, `GET /health` jalan.

### Phase 3 — Database Schema & Migrations
- Define semua schema Drizzle (`db/schema/*.ts`)
- Define relasi (`db/relations.ts`)
- `drizzle.config.ts` setup
- Generate & jalankan migrasi pertama
- `db/seed.ts` — seed admin default + sample data

**Deliverable:** Semua tabel ada di DB, ada admin default.

### Phase 4 — Middleware & Auth Module
- `middlewares/error.middleware.ts`
- `middlewares/logger.middleware.ts`
- `middlewares/auth.middleware.ts`
- `middlewares/role.middleware.ts`
- `utils/password.ts`, `utils/jwt.ts`
- Module `auth/` — `POST /auth/login`, `GET /auth/me`

**Deliverable:** Bisa login, dapat JWT, JWT bisa diverifikasi.

### Phase 5 — Master Data Modules
Implementasi CRUD untuk:
- `users/` (admin only)
- `bahan-baku/`
- `suppliers/`
- `menus/` (+ sub-resource: resep menu)

**Deliverable:** Semua master data bisa di-CRUD.

### Phase 6 — Transactional Modules (Core POS)
- `pesanan/` — buat pesanan + detail, update status
  - **Side-effect:** saat status → `completed`, otomatis insert ke `Transaksi_Bahan_Keluar` (kurangi stok via resep)
- `pembayaran/` — catat pembayaran per pesanan

**Deliverable:** Flow kasir end-to-end jalan.

### Phase 7 — Inventory Modules
- `pesanan-bahan/` — buat PO ke supplier
- `transaksi-masuk/` — terima bahan (otomatis update status PO + tambah stok)
- `transaksi-keluar/` — pengeluaran manual (waste, damaged, dll)

**Deliverable:** Manajemen stok lengkap.

### Phase 8 — Reports & Polish
- `laporan/` — endpoint agregasi:
  - `GET /laporan/pemasukan?from=&to=`
  - `GET /laporan/pengeluaran?from=&to=`
  - `GET /laporan/laba-rugi?from=&to=`
  - `GET /laporan/stok-rendah`
  - `GET /laporan/menu-terlaris`
- Testing menyeluruh
- Dokumentasi API (OpenAPI/Swagger via `@hono/zod-openapi`)

**Deliverable:** API production-ready.

| Aspek | Convention | Contoh |
|---|---|---|
| File | `kebab-case.ts` | `bahan-baku.service.ts` |

## 7. Future Extensibility — Catatan Jangka Panjang

Struktur ini dirancang untuk mudah menerima fitur tambahan tanpa refactor besar.

### Fitur yang mungkin ditambahkan & cara menambahkannya:

| Fitur Masa Depan | Pendekatan |
|---|---|
| **Multi-outlet / cabang** | Tambah tabel `outlet`, kolom `outlet_id` di tabel transaksi, scope query di middleware |
| **Diskon & Promo** | Tambah modul `promos/`, tabel `promo` + `pesanan_promo`, hitung di service `pesanan` |
| **Pajak (PPN/service)** | Tambah kolom `pajak`, `service_charge` di `Pesanan`, hitung di service |
| **Member / Loyalty** | Tambah modul `members/`, tabel `member` + `poin_transaksi`, kolom `member_id` di `Pesanan` |
| **Print receipt** | Tambah module `receipts/` generate PDF/ESC-POS |
| **Kitchen Order Ticket** | Tambah event-based system + WebSocket / SSE |
| **Audit log** | Tambah tabel `audit_log` + middleware otomatis catat perubahan |
| **File upload (gambar menu)** | Tambah service `storage/` (S3/local), kolom `image_url` di Menu |
| **Notifikasi (low stock)** | Tambah service `notifications/` + cron job / event listener |
| **Refund / Void transaksi** | Tambah status `refunded` di `Pesanan`, kebalikan stok via `Transaksi_Bahan_Masuk` |
| **Shift kasir** | Tambah tabel `shift`, kolom `shift_id` di `Pesanan` + `Pembayaran` |
| **Stok opname** | Tambah modul `stock-opname/` + tabel `opname` |

### Prinsip yang Dijaga
1. **Modular** — fitur baru = modul baru, tidak menyentuh modul lain.
2. **Service layer terpisah** — business logic tidak bocor ke route/handler.
3. **DB schema versioned** — semua perubahan via migration, tidak edit langsung.
4. **Side-effect explicit** — efek samping (kurangi stok, update status) dilakukan di service dalam transaction DB.
5. **API versioning siap** — semua route mount di `/api/v1`, mudah tambah `/api/v2`.
